# 本地记忆是怎么帮你省（或亏）Token 与时间的：一笔谁都能算清的往返账

**[简体中文](token-economics.md) · [English](../token-economics.md) · [返回文档中心](README.md) · [返回仓库主页](../../README.md)**

很多记忆工具喜欢宣传一个固定的百分比（比如“立省 70% Token”）。但只要你用过 AI 编程助手（Claude Code、Cursor、Codex、ZCode 等），就知道实际情况千差万别：有时候它一跳帮你找到了关键文件，省下好几轮折腾；有时候它没搜到有用的东西，反而白白多跑了一轮工具调用。

与其报一个好看的宣传数字，不如我们把这笔账摊开，用谁都能验证的加减乘除算清楚：**在日常长上下文工作里，本地记忆到底是怎么省 Token 和时间的？在什么情况下不仅不省、反而倒贴？**

---

## 1. 先看基本事实：Agent 每多一次往返，到底花掉了什么？

大语言模型本身是无状态的。当你的 AI 编程助手在执行一个多步任务时，它并不是“只把最新一句话发给模型”，而是运行在一个**工具调用循环（Agent Loop）**里：

- **第 1 轮**：发送 `[系统提示词 + AGENTS.md + 你的问题]`（假设初始约 `20,000` tokens）$\rightarrow$ 模型思考并调用工具；
- **第 $t$ 轮**（长程任务进入中后段，读过了多个代码文件、日志和工具输出，真实工作场景下大家的当前上下文通常都在 **$C_t = 100\text{k} \sim 400\text{k}$ tokens** 之间，我们取中间值 **$200,000$ tokens** 为例）：
  只要 Agent 还需要再调用一次工具（比如再跑一次 `grep` 或 `Read`），客户端就必须把这 **$200,000$ tokens 的当前完整上下文重新作为输入（Input Tokens）发给模型计费一次**，再加上模型当轮生成的输出 Token（$O_t$），以及这次工具返回的新增内容（$\Delta C_t$）。

> **那开启了 Prompt Caching（提示词缓存）呢？**
> 即使命中缓存，缓存读取依然按“当前上下文总长度 $C_t$”按轮计费（通常为原价的 10%～25%，未命中或跨缓存窗口时按 100% 计费），而且每一轮都实打实地要多等一次网络传输、模型首字延迟（TTFT）、输出生成和本地工具执行的时间（通常 3～15 秒/轮）。

这就得出了一个非常朴素的结论：

> **在长上下文场景下，决定一次工具调用贵不贵的，往往不是这次工具返回的那几百个字，而是“为了多走这一轮往返，必须把当前已经很长的上下文 $C_t$ 再重读一遍”。**

## 2. 命中一次记忆能省多少？（正向算账：以 100k–400k 长程上下文为例）

在真实的长程开发任务里，大家的上下文尺寸基本都在 **`100k ~ 400k` tokens** 之间。我们取 **$C_t = 200,000$ tokens** 来算一笔实账。假设你问 Agent：“*上次那个状态栏闪烁的问题是怎么修的？*”

### 情况 A：没有记忆，Agent 靠盲搜试错

因为代码里的变量名不叫“闪烁”（比如叫 `sseStreamDebounce`），Agent 通常会这样找：
1. **第 1 次往返**：调 `grep "闪烁"` $\rightarrow$ 0 条命中（重读 `200,000` tokens + 耗时 6 秒）；
2. **第 2 次往返**：调 `find / glob` 找前端目录列表 $\rightarrow$ 返回一堆文件名（重读 `200,500` tokens + 耗时 6 秒）；
3. **第 3 次往返**：猜了两个文件调 `Read` 进去看 $\rightarrow$ 发现不是（重读 `203,000` tokens + 耗时 9 秒）；
4. **第 4 次往返**：换关键词调 `grep "status"` $\rightarrow$ 终于找到目标文件 `dashboard.vue`（重读 `206,000` tokens + 耗时 7 秒）。

光是为了“找到该看哪个文件”，这 4 次往返累计产生了约 **`809,500` 输入 Tokens（超过 80 万 Tokens）** 的账单基数，耗时 **28 秒**。

### 情况 B：调用一次 `recall` 命中了历史记录

1. **第 1 次往返**：Agent 调用 `recall(cue="状态栏闪烁")` $\rightarrow$ 本地 SQLite 在几十毫秒内返回上次排障记录（约 `400` tokens），里面直接写着入口在 `dashboard.vue` 的 `sseStreamDebounce`（重读 `200,000` tokens + 耗时 6 秒）；
2. **紧接着**：Agent 直接 `Read` 目标文件开始干活，省掉了中间那 2～3 次盲目试错。

**账单对比**：
- **哪怕这次 `recall` 只帮你少走了 1 次盲搜往返**：按 `100k ~ 400k` 的日常长程上下文计算，单次省下的就是 **`100,000 ~ 400,000` 输入 Tokens**（在 `200k` 算例下就是整整 **`200,000` tokens**）和 **5～10 秒等待时间**；
- **如果帮你少走了 2～3 次盲搜往返**：省下的就是 **`200,000 ~ 1,200,000`（20 万到上百万）输入 Tokens** 和一二十秒等待时间；
- 而且因为 Rolling Memory 本身在本地 SQLite 运行，**这次 `recall` 在记忆层花费的模型费是 $0、向量 API 费是 $0**。

这就是我们在 README 里说的：**在 `100k ~ 400k` 的长程上下文场景中，哪怕只命中一次、只减少一两次往返，省下的也是当前长上下文的单次（或数次）总 Token——能省一点是一点。**

## 3. 什么时候不仅不省、反而会亏？（反向算账与亏损反例）

科学的态度不能只报喜不报忧。上面“省 Token”的结论**并不是无条件成立的**。只要出现下面三种情况，调用记忆不仅不省，反而会多花 Token：

### 反例 1：调用了 `recall`，但没查到有用信息（或返回了一堆噪音）

如果当前问题在记忆库里压根没有记录，或者词法检索没匹配上：
- Agent 先花了 **1 次往返** 调 `recall`（在 $C_t = 200,000$ tokens 时重读了一次 `200,000` tokens，假设还返回了 $R = 600$ tokens 的无关片段塞进了上下文）；
- 发现没用之后，Agent **还是得照常去跑那 3～4 次 `grep` 盲搜**。
- **结果（净亏损）**：你不仅一分钱没省下，反而**净亏了 1 次完整长上下文重读（`100k ~ 400k` tokens）+ 后续每一轮都要多背着的 `600` tokens 噪音**，时间也多花了五六秒。

### 反例 2：上下文很短，且你已经知道准确的文件名或函数名

如果刚开新会话（$C_t = 3,000$ tokens），你直接问“把 `parseConfig` 函数的第 20 行改一下”：
- Agent 直接调一次 `grep "parseConfig"` 就能 100% 定位；
- 如果这时候再去调一次 `recall`，纯属多此一举，白白多走一轮往返。

### 反例 3：每次注入的记忆片段过长、噪音过多，且后续还要聊几十轮

如果记忆工具每次不加筛选地往你的上下文里塞入 `5,000` tokens 的冗长历史对话（$R = 5,000$），而后续这个长程会话还要继续跑 40 轮：
- 那么这 `5,000` tokens 会在后面 40 轮里被反复重读 40 次，累计增加 $40 \times 5,000 = 200,000$ tokens 的负担，直接抵消掉少走一次 `200k` 往返省下的 Token！

## 4. 盈亏平衡公式：怎么判断它对你到底是赚是赔？

把正反两面合起来，假设在你的日常任务中：
- 触发 `recall` 时的平均上下文长度为 $C$（长程任务通常为 `100,000 ~ 400,000` tokens）；
- `recall` 自身返回并留存在上下文里的文本长度为 $R$（tokens），后续平均还要继续交互 $m$ 轮；
- `recall` 真正帮上忙的概率（有效命中率）为 $p \in [0, 1]$；
- 一旦帮上忙，平均能帮你减少 $k$ 次盲搜往返（$k \ge 1$）。

那么，每次调用 `recall` 的**期望净节省 Token 数**为：

$$\mathbb{E}[\Delta \text{Tokens}] \approx \underbrace{p \cdot k \cdot C}_{\text{命中时省下的盲搜往返}} - \underbrace{\bigl(C + m \cdot R\bigr)}_{\text{recall 自身花掉的 1 次往返 + 注入体积负担}}$$

从这个极其简单的式子，一眼就能看出盈亏边界：

$$\text{要想净赚（}\mathbb{E}[\Delta \text{Tokens}] > 0\text{），必须满足：}\quad p \cdot k > 1 + \frac{m \cdot R}{C}$$

- **举例 1（稳赚场景）**：在 `100k ~ 400k` 的长程上下文中（取 $C = 200,000$），每次返回经过降噪的精简片段（$R = 500$，后续 $m = 10$ 轮，$\frac{mR}{C} = \frac{5,000}{200,000} = 0.025$，即注入片段本身的体积负担只有 **2.5%**）。只要你只在“确实需要查历史/找坐标”时调用（比如有效命中率 $p = 50\%$），且命中一次平均少走 $k = 2.5$ 次盲搜，那么 $p \cdot k = 1.25 > 1.025$，平均每调一次净省约 **$45,000$ tokens**。
- **举例 2（稳赔场景）**：如果不分青红皂白每句话都调 `recall`（导致有效命中率掉到 $p = 10\%$），哪怕命中时能省 3 次往返（$p \cdot k = 0.3 < 1$），长期算总账也一定是亏的。

## 5. 顺便算一笔账：为什么我们不让 LLM 在写入时做抽取总结？

很多人会问：如果让 LLM 在入库时把对话抽取成简短的一两句话，将来 `recall` 拿出来消费的时候（即公式里的 $R$），每次不就能少占几十、几百个 Token 吗？

没错，**“消费时每次可能省几十、几百个 Token”确实是 LLM 抽取总结唯一显而易见的好处。** 但只要把这笔账放到 `100k ~ 400k` 的真实往返里对比一下，就会发现它往往得不偿失：

1. **消费端省下的那点 Token 非常有限**：在每次往返动辄 `100k ~ 400k` tokens 的长上下文里，检索结果 $R$ 是 `500` tokens（降噪后的原文片段）还是 `200` tokens（LLM 抽出来的摘要），两者只差了 `300` tokens——占单次往返的比例不到 **0.15%**。
2. **写入端却要先付出一笔昂贵的“LLM 理解成本”**：为了省下将来（还不一定会被查到的）那几十、几百个 Token，用户在写入时必须先为 LLM 阅读和总结买单：
   - **方式 A（Agent 在工作往返中随手记）**：如果让正在干活的 Agent 调一个 `remember / save_memory` 工具去写总结，这1次工具调用本身就会**立刻多走 1 次 `100k ~ 400k` 的完整上下文往返**——为了将来省几百个字，当场先花掉二三十万 Token！
   - **方式 B（专门的旁路 LLM 阅读上下文提取）**：如果每一轮对话都在后台把上下文发给旁路大模型去阅读、理解、抽三元组或做显式记忆迭代，那你每一轮都在额外支付一整套旁路大模型的阅读与生成账单。

所以，我们选择不在写入时花 LLM 的钱去改写和总结，也不让 Agent 在干活中途调写记忆工具，而是直接用本机程序零成本做结构降噪、原样存进 SQLite。

### 6.5 如何随时关掉体验评价 Hook？

本地模式下默认启用了轻量 Hook 与评价卡，就是为了让你也能直观看到上面的效果。如果你觉得不需要、或者想保持上下文绝对干净，随时可以用下面的命令关掉：

```bash
# 方式 1：重新挂载为纯 MCP 工具模式（只保留 recall 工具，移除所有 Hook 与指令提示）
rolling-memory install --mcp-only

# 方式 2：保留安装，单独关闭 Hook 账本记录
rolling-memory config set hooks.ledger false
```

## 7. 这就是我们正在努力的方向（也是诚邀你一起参与的地方）

看懂了上面的盈亏公式 $\left(p \cdot k > 1 + \frac{m \cdot R}{C}\right)$，你就完全明白为什么 Rolling Memory 要这样设计，以及我们还在努力改进什么：

1. **把记忆层自身的账单降到 0**：不用大模型抽取、不用收费向量 API、不用云托管，确保公式右边不会再额外加上一笔“后台隐性模型税”。
2. **让 Agent 按需调用，而不是每轮无脑强塞**：只保留一个 `recall` 工具，明确要求 Agent 在“知道坐标时直接干活，遇到历史缺口或卡住时再查记忆”，避免在反例 2 的场景里白跑往返。
3. **持续改进降噪（缩小 $R$）与召回准确率（提高 $p$）**：
   - 我们正在持续打磨**结构降噪**（剥离工具刷屏日志、`<thinking>` 和重复块），让每次返回的 $R$ 尽可能短小精悍；
   - **我们也在持续优化本地词法与统计检索**，努力把有效命中率 $p$ 往上提。顺便提一句：虽然纯词法检索在真人闲聊测试集上会漏掉那些“词面没有交集”的句子（比如口语里把“张三”叫“老张”，或者“这个项目、那个人……做完了”之类的主语省略与指代不清），但在你的 **Harness Agent 编码场景**下，使用同一个模型围绕同一个项目开发，输出用词一致、表述规范，基本不会出现语病和指代不清，天然契合词法分析架构，实际有效命中率 $p$ 往往比口语闲聊场景更稳。

**我们不承诺它对每个人的每个任务都一定省 Token。** 你可以随时在实际使用中对照上面的公式检验它——如果发现它在某类问题上总是未命中、或者返回了太多噪音，非常欢迎直接提 Issue、给出批评建议，或者提交代码和我们一起把它改好！
