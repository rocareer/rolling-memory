# 既然 Harness 自带 `grep`，为什么还要用 `recall` 与 `Background` 目录挂载？（边界、价值与自证指南）

**[简体中文](background-vs-grep.md) · [English](../background-vs-grep.md) · [返回文档中心](README.md) · [返回仓库主页](../../README.md)**

很多开发者第一次看到 Rolling Memory 支持挂载任意本地目录（`L1 Background`）时，都会问一个非常直接的问题：

> *“既然 `Background` 可以挂载任何目录——比如我直接把代码仓库添加进来，`recall` 就能搜到里面的记录——那这不就是多此一举吗？我的编程助手（Harness）本来就能直接调 `grep` / `ripgrep`，你们的价值到底在哪？又该如何证明？”*

这个问题问到了点子上。**如果你只是想在「当前已经打开的工作区代码库」里找一个已知的函数名或精确字符串，把整个当前代码仓库挂进 `Background` 去替代 `grep`，不仅多此一举，甚至可能倒贴 Token。**

我们从不把 Rolling Memory 包装成“`grep` 的替代品”。本文把两者的边界彻底摊开：先讲清楚**什么情况下你完全应该直接用 `grep`**，再讲清楚**单靠 `grep` 扫当前工作区办不到的 4 件事**，最后给出 **3 套可以直接在你自己电脑上当场跑出来的验证方法**。

---

## 1. 先立边界：什么时候调 `recall` 确实是“多此一举”？

在 [`token-economics.md` 第 3 节](token-economics.md)的反例中，我们明确列出了**不该用 `recall`、而应该直接用 `grep` / `Read`** 的场景：

1. **当前工作区 + 已知精确符号 = 直接用 `grep`，别调 `recall`**
   - 当你对 Agent 说：*“把 `parseConfig` 函数的第 20 行改一下”*，或者 *“搜一下当前仓库里所有调用 `NewVault` 的地方”*；
   - 此时 Harness 直接调一次 `grep "parseConfig"` 就能在几毫秒内 100% 定位到当前工作区的活体代码。如果这时候再去调一次 `recall`，纯属白白多走一轮工具往返。
2. **不要把整个庞大、高频改动的当前代码仓无脑全量挂进 `Background` 当普通全文搜索用**
   - 当前工作区的源码文件本来就在你的磁盘上，Agent 随时可以用 `grep`、`glob` 和 `Read` 直接读取最新字节；
   - Rolling Memory 的核心设计是 **「L2 跨会话历史（Episodic）+ L3 提炼关联（Noetic）+ L1 跨目录/异构参考资料（Background）的联合检索」**。

那么，既然 Harness 已经有 `grep` 了，`recall` 与 `Background` 挂载真正不可替代的价值究竟在哪？

---

## 2. 单靠 `grep` 办不到的 4 个核心价值

| 对比维度 | Harness 自带 `grep` / `ripgrep` | Rolling Memory（`L2 会话历史` + `L3 关联记录` + `L1 背景挂载`） |
|---|---|---|
| **1. 只记得症状、不记得变量名** | **必须猜中代码里的准确字面词**：代码里变量名叫 `sseStreamDebounce`，`grep "闪烁"` 返回 `0` 条结果，Agent 往往要猜关键词跑 3～5 轮 `find` / `grep` / `Read` 试错。 | **从过往排障对话桥接到代码坐标**：过去的会话里聊过“状态栏闪烁是因为 `dashboard.vue` 的 `sseStreamDebounce`”，搜症状即可一跳拿到当时的文件路径与行号锚点（如 `#L45-82`）。 |
| **2. “为什么不能那样写”的排障教训** | **代码里只有最终留下的写法，没有被放弃方案的原因**：源码里通常搜不到 *“为什么上周试过方案 A 后来回滚了？”*，新开会话的 Agent 极易重踩死胡同。 | **留存失败尝试与决策原话**：把当时报错栈、回滚原因和跨文件联动约定原样保存在本地库中，下次遇到同类问题直接查出前因后果。 |
| **3. 跨目录视野与二进制办公文档** | **通常受限于当前工作区纯文本**：默认只扫当前打开项目的纯文本源码，遇到跨仓库目录或 `.docx` / `.xlsx` / `.pptx` / `.pdf` 二进制规范文档即束手无策。 | **跨目录挂载 + 零依赖解析二进制文档**：支持挂载工作区之外的关联仓库与文档目录，原生流式解析 Word / Excel / PPT / PDF，原位按需读取且不冗余拷贝大文件。 |
| **4. 常见词刷屏 vs. 多线索共现排序** | **平铺无序刷屏**：在大仓库搜 `timeout` 或 `token` 会吐出上千行平铺匹配，混杂大量测试夹具与无关文件，极易塞爆上下文。 | **自适应信息量与多线索共鸣排序**：结合本地记忆库词项稀有度、跨形式确定性对齐（日期、词形、数字×单位）与紧凑时间窗共现，直接交付信息密度最高的 Top-K 片段。 |

下面具体展开这四件事：

### 价值一：「自然语言症状 $\rightarrow$ 真实代码符号」的跨层桥接（最核心的省轮次场景）

`grep` 的本质是严格子串或正则匹配。但在日常开发中，你向 Agent 提问时往往描述的是**现象、业务意图或上次印象**：
- *“上次那个切换状态栏闪烁的问题是怎么修的？”*
- *“为什么大库检索在冷启动时会卡住？”*

因为源码里的函数名通常叫 `sseStreamDebounce` 或 `pruneLargeVaultHydrationCandidates`，源码注释里也未必有“闪烁”这两个字：
- **只靠 `grep` 时**：Agent 第 1 轮 `grep "闪烁"`（0 命中）$\rightarrow$ 第 2 轮 `glob` 翻目录列表 $\rightarrow$ 第 3 轮猜两个文件 `Read` 进去看发现不对 $\rightarrow$ 第 4 轮换英文词再 `grep`。在日常 **`100k ~ 400k` tokens** 的长程上下文里，每多试错一轮，客户端都要把当前这几十万 Token 的完整上下文重新发给大模型计费一次（详见 [`token-economics.md`](token-economics.md)）。
- **配合 `recall` 时**：`recall` 会**同时检索 L2 过往对话 + L3 历史引证关联 + L1 背景文档**。只要之前的对话或文档里提过这次排障，`recall` 在几十毫秒内就能把当时的讨论原话连同精确文件坐标一并交还给 Agent，让 Agent 一步直达 `Read` 目标文件，省掉中间那几轮盲目试错。

### 价值二：记住代码里看不见的「否定性知识」（为什么不能那样改）

源码仓库的当前 `HEAD` 只保留了**“最终留下来的代码长什么样”**，却不会保留**“为什么另外三种看似更简单的写法是错的”**。

比如：
- 在 macOS 上更新正在运行的二进制文件，为什么代码里写成了看似啰嗦的“同目录写临时文件再 `mv -f`”，而不能直接 `cp` 覆盖？（因为直接 `cp` 覆盖运行中进程映射的同一 inode 会触发内核签名校验失败，导致进程挂死。）
- 为什么某个 SQLite 查询不能加某条看似合理的索引，或者为什么改了文件 A 必须同步更新文件 B？

当你第二天新开一个会话让 Agent 重构代码时，`grep` 扫遍全仓也告诉不了它这些历史血泪教训；而 `recall` 能从过往排障对话里把当时的报错现场和否决理由原封不动捞出来，防止 Agent 把你三天前刚修好的坑再改回去。

### 价值三：`L1 Background` 真正的主场——「跨仓库参考」与「二进制办公文档（`.docx/.xlsx/.pptx/.pdf`）」

既然当前工作区的纯文本源码可以直接 `grep`，那 `L1 Background` 目录挂载到底该怎么用才最划算？它主要解决 `grep` 的两个物理盲区：

1. **挂载「当前工作区之外」的关联规范、跨仓协议或沉淀文档目录**
   - Harness 的搜索工具默认锁定在当前打开的单一项目目录。但实际开发中，你写前端时需要查后端仓库的 API 定义，写业务插件时需要查核心 SDK 的契约文档，或者你有专门存放架构设计、会议纪要的独立知识库目录；
   - 把这些目录通过 `rolling-memory background add --path <dir>` 挂进 `Background`，Agent 无需切换工作区，一次 `recall` 就能把跨目录规范和当前项目的历史讨论一起取回。
2. **原生流式解析 `grep` 扫不动的二进制办公文档**
   - 很多团队的产品需求、接口台账、测试矩阵保存在 Word（`.docx`）、Excel（`.xlsx`）、PowerPoint（`.pptx`）或 PDF（`.pdf`）里，普通 `grep` 扫上去只能看到二进制乱码；
   - Rolling Memory 内置了零外部依赖的纯 Go 多格式文档读取器，支持直接提取并按 **`1024 tokens/块`** 切分以下格式：
     - **办公与排版文档**：`.docx`（段落与表格）、`.xlsx`（多工作表行块，带 `Sheet1:r1-15` 坐标）、`.pptx`（幻灯片文本，带 `slide3` 坐标）、`.pdf`（文本流，带 `page2` 坐标）；
     - **结构化与文本文档**：`.md`、`.txt`、`.rst`、`.json`、`.jsonl`、`.csv`、`.tsv`、`.yaml`、`.yml`、`.toml` 及主流源码文件（带 `#L1-60` 精确行号坐标）。
3. **原位按需读取（不把你的文件复制一遍塞进数据库）+ 改动自动联动失效**
   - 挂载目录时，SQLite 金库**不会**把几百 MB 的原始文档冗余拷贝进数据库，而是只存轻量元数据（绝对路径、`mtime`、文件大小、内容 `SHA-256` 与分块偏移索引）；
   - 当 `recall` 命中某个分块时，直接从磁盘原文件毫秒级按需读取最新内容；
   - 执行增量同步（`rolling-memory background sync`）时，未改动的文件通过 `os.Stat` 在 $O(1)$ 时间内直接跳过；一旦原文件被修改，系统会自动重切变化的分块，并将此前引用过旧分块的 `L3 Noetic` 关联记录自动标记为 `stale`（过期），绝不拿旧缓存误导当前任务。

### 价值四：多线索信息增益排序 vs. `grep` 的无序匹配刷屏

当你在中大型项目里调查一个涉及多个概念的问题（例如同时涉及 `timeout`、`sqlite`、`busy` 或某个日期与错误码组合）：
- `grep` 只能按单个正则表达式逐行扫描，搜常见词会瞬间吐出几百上千行匹配，测试假数据、注释和核心实现混成一团，不仅浪费上下文 Token，还得靠人工或 Agent 翻好几页去筛；
- Rolling Memory 的本地检索内核结合了 **在线自适应词项稀有度（同日重复粘贴的刷屏日志自动按对数折叠）**、**跨形式确定性对齐（如自然语言日期 `"May 12, 2025"` 与 ISO `"2025-05-12"`、词形变体、复合标识符、`500ms`/`16GiB` 等数字单位对）** 以及 **多线索紧凑时间窗共鸣**，直接把同时命中多个高信息量线索的片段排到最前面交付出来。

## 3. 如何证明这不是空口宣传？（3 套你随时能自己跑的验证方法）

科学的工具经得起证伪。你不需要相信任何静态宣传，可以直接用下面三种方法在自己的机器上核验：

### 证明方法一：用内置的「零模型事后证据复用审计」看可观察的证据复用

在 [`token-economics.md`](token-economics.md) 中，我们给出了每次调用 `recall` 的盈亏平衡条件：

$$p \cdot k > 1 + \frac{m \cdot R}{C}$$

（其中 $C$ 是当前上下文长度如 `200k` tokens，$R$ 是召回结果体积，$p$ 是有效命中率，$k$ 是命中时少走的盲搜轮数。）

为了独立交叉验证有效命中率 $p$（不依赖自评），系统内置了一套**完全不调用大模型、100% 确定性的事后反回声证据复用审计**：
- **审计逻辑**：每当 `recall` 返回了一批文件路径或符号锚点，本地审计器会检查当前会话**后续的工具输入与回复正文**（剥离仅回声查询本身的文本）：
  - 如果召回交付的文件路径或符号出现在后续 `Read` / `Edit` 工具输入中，记为 **`adopted_tool`（工具输入匹配）**；
  - 如果剥离提问本身的回声词后，召回片段里的独有事实出现在后续回复中，记为 **`adopted_context`（回复匹配）**；
  - 如果已结算的后续窗口里没有出现任何交付锚点，**如实记为 `unadopted`（未观测到匹配）**。这只是观察结果：未观测到匹配不等于没有用，匹配也不证明省下一步。
- **我们主力开发机的观察底账**：
  - 在平均单次上下文 `272.0k ~ 320.1k` tokens 的真实开发负载下，长期保留账本（440 条已完成审计的召回）中，交付锚点后来出现在工具输入或回复里的比例为 **`61.1%`（269/440）**；最近 24 小时窗口为 **`89.1%`（41/46）**；
  - 在最近 24 小时的 33 份去重逐轮实名评价卡中，**有 6 份（18.2%）诚实记为「0 节省」**，另外 **27 份（81.8%）累计省下 `116` 次盲搜往返（平均每次命中省 `4.3` 次）**——按此节奏推算，单台重度开发机一周净省约 **`791` 次长上下文往返（约 `1.58 亿` Input Tokens）**（完整正反明细见 [`token-economics.md` §6](token-economics.md)）。
- **在你自己的电脑上查看**：运行 `rolling-memory panel` 打开本地 Web 控制台（访问 [http://localhost:8008/#/admin](http://localhost:8008/#/admin) 的 ROI 监控屏），你自己的每一次 `recall` 交付锚点是否在后续工具输入/回复中再次出现（匹配），或仍处于待结算窗口，逐条都有账可查；单一匹配与否都不足以证明省了或白跑一轮。

### 证明方法二：在公开学术基准上断网一键复现

普通子串匹配或基础 BM25 在面对多线索、跨表述的长程问题时召回率会大幅下滑。我们在剑桥大学公开的 **ATM-Bench**（11,034 条多源个人记录）和 **LoCoMo**（1,540 道长对话问题）上，纯靠这套本地无向量、无写入期 LLM 的检索内核取得了以下可复算结果：
- **ATM-Bench Main（1,013 题）**：官方 `Recall@10`（逐题金标覆盖率均值）**`82.77%`**（辅助 `Any-Hit@10` 为 `85.29%`；现行产品臂，2026-11-20 复核）；
- **ATM-Bench Hard（31 道高难多跳题）**：官方 `Recall@10` **`52.43%`**（辅助 `Any-Hit@10` 为 `80.65%`）；
- **LoCoMo 全量（1,540 题）**：端到端判对率 **`85.26%`**。

你可以直接用一条命令拉取带 `SHA-256` 封条校验的上游公开语料，在本机断网跑完检索评测并从原始 JSONL 逐题核对（详见 [`benchmarks.md`](benchmarks.md)）：

```bash
# 1. 拉取上游公开语料并在本地校验 SHA-256 摘要（约 35 MB）
rmem eval --fetch-only --fetch atm --accept-upstream-license

# 2. 完全离线运行 Main-1013 与 Hard-31 纯本地检索评测（0 模型调用、0 网络请求）
rmem eval --suite atm --tier 1013 --answerer none --judge off --top-k 50
rmem eval --suite atm --tier hard --answerer none --judge off --top-k 50
```

### 证明方法三：10 秒钟本机「`grep` vs. `recall`」同台对比

在你日常使用过几天后，打开终端挑一个**“只说故障现象或历史原因、不提代码变量名”**的问题做一次对比：

```bash
# 1. 用 grep 在代码仓里搜自然语言症状或“为什么不用某方案”——通常返回 0 条或一堆无关注释
grep -rn "状态栏闪烁" .

# 2. 用 rmem recall 检索同一句话——直接返回当时讨论该问题的对话原文、原因与精确文件路径 #Lx-y
rmem recall --cue "状态栏闪烁"
```

## 4. 实用建议：怎么把 `grep`、`recall` 与 `Background` 配合到最佳状态？

1. **查当前仓库的已知函数名 / 变量名 / 精确字符串 $\rightarrow$ 直接让 Agent 用 `grep` / `ripgrep`**
   这是 `grep` 的绝对主场，最快、最准，不需要绕道记忆库。
2. **查历史排障原因、模糊症状定位、跨会话上下文 $\rightarrow$ 调 `recall`**
   先用一次毫秒级本地 `recall` 把模糊问题变成精确的「文件路径 + 行号 + 历史决策原因」，再用 `Read` 或 `grep` 去看最新代码。
3. **挂载 `Background` 目录时讲究“少而精”**
   优先挂载**架构与产品规范目录、含 `.docx` / `.xlsx` / `.pptx` / `.pdf` 的参考资料目录、或当前工作区之外需要跨仓对齐的关联项目目录**：
   ```bash
   # 挂载外部设计文档或跨仓协议目录
   rolling-memory background add --path ~/work/shared-specs

   # 查看已挂载目录与增量同步状态
   rolling-memory background list
   rolling-memory background sync
   ```
