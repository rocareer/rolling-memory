## Q1：跟普通文档检索、`grep` / `ripgrep` 有什么区别？`grep` 也能做到很多事情啊！

**简答**：`grep` 是**「当你已经知道准确变量名或字符串时，去扫描当前代码库的工具」**；而 Rolling Memory 是**「帮你从过往对话和排障记录里找回当时说了什么、改了哪个文件的工具」**。两者不是替代关系，而是配合使用的：**先用 Rolling Memory 把模糊的问题描述对应到当时的历史记录和文件路径，再用 `Read` 或 `grep` 去看最新的活体代码。**

在日常开发中，单靠 `grep` 扫当前代码库有几件事很难办到，而这正是本地记忆库补位的地方：

| 对比维度 | 普通代码扫描（`grep` / `ripgrep`） | Rolling Memory（本地原文金库 + 词法统计检索） |
|---|---|---|
| **1. 只记得症状、不记得变量名** | **必须猜中代码里的准确字面词**：当你问 *“上次那个切换状态栏闪烁的 Bug 在哪修的？”*，如果代码里变量名叫 `sseStreamDebounce`，`grep "闪烁"` 返回 `0` 条结果，Agent 往往要猜关键词跑好几轮 `find`/`grep` 试错。 | **从过往讨论定位文件坐标**：只要之前的对话里聊过这次排障，记忆库里就存着当时的原话和涉及的文件路径（如 `admin/.../dashboard.vue`），搜症状就能把当时的定位找出来。 |
| **2. “为什么不能那样写”的排障教训** | **代码里只有最终留下的写法，没有当时放弃某个方案的原因**：源码里通常搜不到 *“为什么之前试过方案 A 后来回滚了？”*，导致新开会话的 Agent 容易把已经踩过的死胡同再踩一遍。 | **留存过往排障与决策原话**：把之前踩坑、回滚和跨文件联动约定（比如“改 A 必须同步刷 B”）的对话原样存下来，下次遇到同类问题可以直接查到当时的原因。 |
| **3. 区分过期讨论与近期决定** | **平铺无时间概念**：旧文档、老注释和近期的改动平铺在一起，搜出一堆匹配行时很难一眼分清哪条已经作废、哪条是最近的决定。 | **带时间戳与时间邻近加权**：每条记录都保留了发生时间，检索时结合时间邻近度与跨天重复降权。 |
| **4. 跨天、跨会话串联线索** | **单点孤立匹配**：只看当前磁盘上的静态文件，无法把前几天不同会话里围绕同一个模块前因后果的讨论串起来。 | **同会话与相邻句共现检索**：结合词族归并、相邻句成对共现与历史引证记录（`cited_unit_ids[]`），把相关的多段历史对话一起取回。 |

## Q2：跟向量数据库（RAG）或让大模型抽取总结的记忆服务（如 Mem0 / Zep）有什么区别？

目前主流的记忆方案大多依赖**在线向量化（Embedding）**或**让大模型在写入时抽取事实摘要 / 构建知识图谱**。那些方法在跨同义词检索或高度概括上有其价值，但在日常 AI 编程助手场景下，我们之所以选择**“保留原话 + 纯本地词法统计检索”**，主要是出于四点务实的权衡：

1. **真免费、实时不用等（零后台模型税与零排队）**：
   - 无需配置 OpenAI / DashScope / Ollama 等向量嵌入模型，无需运行外部向量库，更不需要在后台排队调用大模型抽三元组；
   - 写入与检索全部是本机确定性计算：刚聊完的对话毫秒级写入本地 SQLite 即刻可查（热缓存单次检索均值约 **`29 ~ 42 ms`**），没有任何后台 Token 账单。
2. **不改写事实，避免“大模型总结错上加错”**：
   - 让大模型在写入时把对话总结成摘要，看似精炼，但一旦当前 Agent 或负责抽取的 LLM 理解偏了，并丢掉了原话，**错误的总结就会被永久固化下来**（所谓“显式记忆迭代”又面临“怎么在它误导后续任务前发现它是错的”的悖论）；
   - 况且，在每次往返动辄 `100k ~ 400k` tokens 的长上下文里，摘要在消费时省下的那几十、几百个 Token 占比不到 `0.15%`，为此在写入时先付出一大笔 LLM 阅读理解成本往往得不偿失（详细算账见 [`token-economics.md`](token-economics.md)）。
   - 因此我们坚持：**历史上发生过的事就是发生过的**——只做确定性的格式清理（剥除协议外壳、`<thinking>` 与重复日志），原话原样入库，这次读到什么样，下次读到还是什么样。
3. **稠密向量容易模糊精确符号，而 Coding Agent 的一致用词天然契合确定性信息检索**：
   - 稠密向量的本质是连续语义平滑——擅长宽泛近义词，却会让 `err_code_4012` 与 `err_code_4013`、端口 `8008` 与 `1828`、`v0.0.1` 与 `v0.0.2`、日期 `2026-05-12` 与 `2026-05-19` 的余弦相似度高达 `0.98` 以上而互相混淆。Rolling Memory 不依赖向量或外部冻结词表，而是结合本地记忆库自适应信息量（带同日重复刷屏日志的对数折叠）、跨形式确定性对齐（日期、词形变体、复合标识符、内联数字×单位）与无量纲多线索事件链共鸣；
   - 在公开的剑桥大学 **ATM-Bench**（11,034 条多模态文本记录）上，本系统纯本地检索取得 Main-1013 官方 `Recall@10`（逐题金标覆盖率均值）**`77.21%`**（辅助 `Any-Hit@10` 为 `80.45%`）、Hard-31 官方 `Recall@10` **`46.12%`**（辅助 `Any-Hit@10` 为 `80.65%`）；
   - 复盘那约 20% 没找到的题目可以发现，它们基本都是**提问与原文在词面上完全没有交集**的真人闲聊情况（比如真人说话把“张三”叫“老张”，或者口语里有大量主语省略和“这个项目、那个人……做完了”式的模糊指代）；
   - 而在你的 **Harness Agent 编码开发**中，你通常使用同一个模型围绕同一个代码库持续工作——AI 表达结构规范，基本不会出现语病和指代不清，讨论的核心又是固定的模块名、函数名、文件路径和报错信息。既然坐在你面前的宿主本身就是能力很强的主力大模型，本地记忆只需以几十毫秒的速度精准翻出零失真原文，把语义推理 100% 交给宿主模型即可（我们在重型向量与图记忆领域其实也很熟悉，团队此前在 LoCoMo 上做出过 **92.79 分**的成绩，这里默认不上向量和图纯粹是出于日常开发性价比的取舍）。

## Q3：各家 Harness 厂商都有自己的记忆功能（如 `CLAUDE.md` / `AGENTS.md`、`MEMORY.md` 自动笔记、Cursor Rules），为什么还要用你们的？

把核心规则写进 `AGENTS.md` / `CLAUDE.md` 或使用宿主自带的 Auto-Memory 是非常好的习惯（我们自己每天也在用），但宿主自带记忆和 Rolling Memory **不是“二选一”的替代关系，而是“桌面精选便签纸”与“全量历史搜索黑匣子”的互补配合**：

1. **宿主自带的自动笔记“写的时候要花钱，而且只记了冰山一角”**：
   - 宿主自带的自动记忆通常靠 Agent 在干活中途主动调一次写文件工具，把几句话存进 `MEMORY.md`。每当 Agent 分心调工具写一次笔记，本身就要**多走一轮 `100k ~ 400k` 的完整上下文往返**；而且那些当时没被写进笔记本的大量对话细节（三天前的报错输出、顺口提过的路径或参数），会话一关就找不到了。
   - Rolling Memory 在后台自动把每轮对话原话零成本收进本地 SQLite，不需要 Agent 调写工具，平时占 `0` 个 Prompt Token；当精选笔记里没记某个细节时，调一下 `recall` 就能从全量历史对话里捞出当时的原话。
2. **常驻文件塞多了会撑爆上下文，按需检索平时不占地方**：
   - `AGENTS.md` 与 `MEMORY.md` 索引会在**每一轮对话无条件全量注入**，适合放几十条核心规则；如果把成百上千条排障记录全塞进去，每轮都会白烧计费 Token 并稀释模型注意力（Lost-in-the-Middle）。
   - Rolling Memory 将长尾历史静默保存在本地库中（静置占 `0` Prompt Token），只有当提问触发相关问题时才按需取回最相关的几百字。
3. **跨工具、跨宿主共享同一个本地记忆底座（打破各家孤岛）**：
   - 你可能同时使用 ZCode、Claude Code、Codex、Cursor、Windsurf 等多个工具。各家厂商自带的记忆是**各自封闭的孤岛**——在 Claude Code 里踩过的坑，换到 Cursor 或 Codex 里就完全不知道了。
   - `rolling-memory install` 一键把 10 个主流宿主挂在同一个本地 SQLite 记忆库上，在任何一个工具里聊过的排障记录，切到另一个工具里调 `recall` 都能直接查出来。
4. **保留未经改写的“第一现场原话”，防止摘要写错后死无对证**：
   - 宿主自动笔记是模型总结出来的几句话，一旦总结时理解偏了，错笔记就会一直误导后续会话；Rolling Memory 不改写事实，保留原始对话切片与出处，随时可以核对当时到底是怎么说的。

## Q4：我的代码和记忆数据存储在自己电脑上，安全吗？会不会有第三方看到？

**本发布版为纯本地模式（`local_plain`）：除了你自己和正在给你干活的那个 Agent，没有任何第三方记忆平台、向量服务商或外部服务器能知道你的代码和信息。**

1. **本机单文件 SQLite 存放与 `0700/0600` 权限隔离**：
   - 本地金库将记忆记录、挂载文档偏移量与检索索引保存在你电脑上的 SQLite 文件里（默认 `~/.local/share/rolling-memory/memory.db`，目录权限 `0700`、文件权限 `0600`，仅当前操作系统属主本人可读写），天然继承 macOS FileVault / Linux LUKS / Windows BitLocker 全盘加密。
2. **记忆平面零出网（注意与下游答题模型的区分）**：
   - 记忆的写入、建索引与检索全程在本地完成，不发任何外部网络请求。历史受众限制可能无法覆盖所有来源；分享召回结果前请先检查内容。
   - 同时我们也把边界说清楚：如果你的编码 Agent 连接的是云端大模型 API（如 Claude、GPT、DeepSeek 等），那么被 `recall` 找出来的那几段原文在跟随当前对话发给大模型作答时，自然会发往你所配置的那个模型服务端。
3. **挂载代码目录原位按需读取（不重复拷贝代码库）**：
   - 挂载本地代码库或文档目录时，SQLite 只记录文件路径与字节偏移量，命中时直接从原文件按需读取，不会把你的整个代码库冗余复制进数据库。
4. **本地数据**：
   - 金库使用 SQLite；所引用的会话文件和挂载文件独立保存。备份限制详见 [privacy.md](privacy.md)。

## Q6：你们的评测分数和省 Token 账单怎么验证？怎么防止针对测试集特调？

**不要轻信任何静态宣传——所有数据和账单都可以直接在你自己的电脑上复现和检验：**

1. **语料自备 + 一键复现命令**：
   - 基准语料不随本仓库分发：请从上游项目获取 LoCoMo 与剑桥大学 ATM-Bench 语料，用 `--eval-data <dir>` 指向你的副本，并以 [benchmarks.md](benchmarks.md) 公布的 `SHA-256` 摘要钉住；两套基准都可一条命令取数——`rmem eval --fetch atm --accept-upstream-license` 会从钉住的 Hugging Face revision 下载必要上游文件（约 35 MB），在本机重建 pinned 语料与题集并对照上述摘要校验，通过后直接开始评测；`rmem eval --fetch locomo --accept-upstream-license` 下载上游 `locomo10.json`（约 2.8 MB）并重建上游官方 cat1-4 题集（1,540 题；便捷档 100/200 不再提供）。随后断网运行 `rmem eval --suite atm --tier 1013 --answerer none --judge off --top-k 50` 即可在本地跑完检索评测，并从生成的原始 JSONL 逐题复算官方 `Recall@10` 与 `Any-Hit@10`。测试在无自带语料时跳过（skip），`rmem eval` 本体则明确报错而不会凭空产出读数。
2. **诚实披露局限**：
   - 我们在 README 中明确写明：这套检索权重和启发式规则在开发过程中针对上述基准做过多轮错误分析与迭代，并非盲测零样本结论，也不是官方榜单正式提交成绩。
3. **自带体验评价 Hook 与真实使用账单**：
   - 本地模式默认开启了体验评价 Hook 与评价卡（不喜欢可随时通过 `rolling-memory install --mcp-only` 或 `rolling-memory config set hooks.ledger false` 关掉）。关于日常长上下文里怎么算省下或亏掉的 Token，以及我们自己开发机最近 24 小时和整周的正反真实账单，请直接查看 [《省 Token 算账与证伪（token-economics.md）》](token-economics.md)。
